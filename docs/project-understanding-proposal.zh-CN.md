# 让 Falsify 审查留下项目理解

日期：2026-10-07。状态：产品提案，供讨论与实现参考；尚未实现，也不改变当前裁决或授权规则。

需求来源：Chris 希望将《Don't delegate understanding》的哲学融入 Falsify，解决自己对项目理解不深、把判断过度交给 AI 的痛点。

## 产品主张

每次 Falsify 审查都应帮助用户建立一个可检查、可解释、可修正的项目模型，留下新增发现与未知；用户实际表达并确认时，再记录理解变化。

分别记录审查结果、用户实际表达、用户确认的修正及仍未知的问题，不记录二元的「是否已理解」。系统生成解释、用户读完报告、用户会复述结论，都不足以证明用户已经掌握项目。

## 哲学来源与我们的转译

Steph Ango（Obsidian CEO）于 2023-08-13 发表 [Don't delegate understanding](https://stephango.com/understand)。文章讨论依赖与激励：当人把理解和控制都交给外部系统时，外部系统可能从持续的依赖中获益；自己建立理解，才能积累自己的收益。

下面是我们将这个观点用于 AI 审查产品的设计推论，并非文章中的原有功能建议：执行可以获得工具帮助；用户应保有解释项目、质疑结论、辨认未知与更新判断的能力。Falsify 的成功应包含用户逐渐能够独立检查关键问题。

## 当前产品的具体切入点

以下依据本机公开仓库源码，未实测线上页面，也不据此推断私有 runtime 的能力：

- `docs/01-architecture.zh-CN.md`：产品定义为证据驱动的决策门；现有闭环为 Frame → Brooks-Lint → Attack → Recompute → Cutline → Receipt。
- `skills/falsify-ai-pr-review/templates/verdict.schema.json`：现有结果包含 summary、findings、minimal_action、next_evidence；这些字段帮助记录问题和行动。
- `falsify/cli.py` 的结构化回执与 `format_review_summary()`：已有范围、对象与证据哈希、原始审查，以及 Why this decision / Need / Next，可作为关联理解产物的入口。
- `web/static/js/home.js` 的 `renderVerdict()`：结果展示裁决、风险、最小行动与升级触发条件。
- `web/console/index.html`：执行台包含白盒 Plan、状态和最近执行结果；术语页帮助辨认裁决边界。
- `templates/audit-sprint.md`：已有 claim manifest、kill-shots、evidence pack 和 verdict receipt，可为机制解释提供素材与范围。

这些是可复用的基础。用户对于被审项目的机制模型、亲自表达过的理解，以及理解变化，需要专门设计。

## 最小体验：在现有结果后展示「项目理解」

### 审查前：可选的一句话

邀请用户写下：「我现在认为这个项目通过 ___ 达到 ___；我最不理解的是 ___。」

允许跳过。只有用户实际提供的文字才可作为审查前的理解；未提供时展示「审查前的理解未记录」。审查报告不替用户补写其过去的想法。

### 审查后：一屏五个问题

| 页面内容 | 帮助用户回答 | 呈现方式 |
|---|---|---|
| 它怎样运转 | 谁遇到什么问题，输入怎样变成结果？ | 一句话目标 + 最短机制链 |
| 它靠什么成立 | 哪些假设或依赖一变，结果就变？ | 最关键的 1–3 条关系，可展开来源 |
| 这次发现了什么 | 哪条证据支持、削弱或推翻了什么判断？ | 发现 → 机制含义 → 支撑材料 |
| 我的理解改变了什么 | 原先的解释，哪些需要修正？ | 用户原话与本次发现并列，修正由用户确认或改写 |
| 还有什么没弄清 | 哪个未知影响当前决定，怎样获得下一条证据？ | 关键未知 → 决策影响 → 下一项验证 |

机制链按需包含：目标 → 输入 → 关键处理 → 输出 → 预期效果；每条关键关系注明「有证据支持」「项目方主张」「推断」「未知」。复杂项目先显示与本次声明有关的最小链，再由用户展开。

「本次发现了什么」必须在用户跳过审查前表达时仍可使用；此时不声称发生了个人理解变化。

### 可选的推演入口

提供「用自己的话解释」和「试着改变一个条件」两个入口，围绕本次真实决策，例如：

> 如果这条关键假设不成立，哪个结果会先变化？你会看什么证据来确认？

系统根据已有证据指出表达中一致、冲突与无法判断的部分，并展示依据。反事实未被测试时标为推演。用户可纠正系统模型，也可保留异议。

不设置通关考试、理解百分比或「已掌握」徽章。记录用户真实表达及可观察的局部推理，用户不参与也可完成原有审查。

### 带走自己的理解

提供 Markdown 导出：当前模型、来源、用户自己的解释、关键未知和下一项验证。用户可以脱离会话阅读、质疑和更新它。

## 一次具体的体验示例

下面是基于仓库 billing migration 样例改写的交互示意，所有用户原话与推演都是示例；不代表本次完成了真实审计。

**审查前，用户表达：**「测试都通过了，我认为迁移后的计费逻辑已得到验证。」

**项目机制：** 请求进入运行路径 → 迁移后的计费逻辑 → 账单结果。当前讨论范围只涉及这次迁移，未覆盖整个计费项目。

**本次发现：** 样例中的测试覆盖旧路径；新运行路径尚未得到这些测试的验证。

**需要修正的理解：** 测试通过说明被执行的路径通过检查；要判断迁移后的逻辑，还需确认测试实际触发新路径并核验账单不变量。

**仍不知道：** 新路径是否被触发、新旧结果是否符合预期。下一条证据是针对迁移路径的不变量测试与运行核验。

**可选推演：**「如果测试继续走旧路径，即便新路径有错误，你预计测试会出现什么现象？」

用户可能仍不熟悉整个计费系统，但能带走一个可应用的机制判断：验证的价值取决于它实际触及的路径，以及它检查的条件。

## 可信边界

1. **范围显式。** 声明级审查只支持该声明及相关机制；全项目未覆盖的部分显式保留为空白。
2. **解释有出处。** 重要事实和关键关系链接原始材料、定位和审查快照；缺少可读取证据时保留未知。未经检验的因果关系标为假设或推断。
3. **三种记录分开。** 项目裁决、系统当前模型、用户实际表达各有来源；用户表达正确不能提高项目 verdict 或 authority ceiling。
4. **变化由证据与原话支撑。** 未记录的旧理解不可被生成；用户未确认的修正不能写成用户已经认同。
5. **新快照提示复核。** 依赖的证据或对象变化时，关联解释提示待更新，不把旧模型当成当前已验证事实。
6. **材料权限继承。** 只使用已授权输入。私人原话、敏感证据与内部推断默认保留在本地私有产物；对外导出允许用户检查与选择内容，不自动发布或发送。

## 首版实现范围

首版应作为一次审查的附属阅读产物，复用已存在的声明、发现和证据。仅在有足够来源材料时生成机制解释；材料不足时展示缺口。

实现顺序：

1. 在审查结果后提供「项目理解」页及 Markdown 导出。
2. 支持可选的审查前表达与用户改写，保存来源和确认状态。
3. 增加针对最关键假设的单次推演及证据反馈。

建议另存理解产物，绑定既有审查快照和可解析的证据引用。原有裁决仍由当前审查与授权流程决定。具体接口和字段在实现时确定。

## 如何判断产品有帮助

设计目标是用户能够更独立地推理，而不是浏览时长或主观信心增加。小规模试用时围绕同一个具体机制，观察用户是否能：

- 用自己的语言解释关键机制，并识别尚无证据的关系。
- 指出最可能改变结论的一条假设，以及它的影响范围。
- 面对一个未照抄报告的变化情景，给出合理预测并找到相应验证材料。
- 说清仍未知的部分，提出与未知直接相关的下一项检查。

以上观察仅说明局部任务中的表现，不构成项目掌握认证。方案有效性尚未通过用户试用验证。

## 建议产品文案

**让每次审查，都留下你对项目更清楚的理解。**

辅助说明：看清它怎样运转，证据改变了什么，以及哪些问题还没有答案。
