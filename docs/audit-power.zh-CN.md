# 审计功率：我们如何量化审计器本身

> 一个不能被攻击的审计器，不配被信任。本页记录私有版 Falsify 引擎如何测量自身的审计能力——用可复现的仪器，而不是形容词。

## 为什么要测「审计功率」

大多数审计工具都在做一个宣称：*「它能抓到问题。」* 但这个宣称很少被量化。一个从未被攻击过的闸门，和死闸门无法区分——它一直是绿的，可能只是因为从没有东西试图闯过去。

Falsify 私有引擎把审计器本身当作被测系统。能力被表达为三个可测量的代理指标，每个都有具名仪器和可复现回执：

| 代理指标 | 测什么 | 仪器 |
|---|---|---|
| **MKR** — 变异击杀率 | 注入的证据篡改是否被抓 | `audit_power_probe.py`（R/D/E 三层，16 个变异算子） |
| **CHR** — 金丝雀命中率 | 审计器能否发现校准造假，而不只是坏数据 | `canary_harness.py`（5 轮，15 次注入） |
| **ACR** — 红队捕获率 | LLM 红队产物是否被拦 | `redteam_corpus_builder.py`（52 件语料，32 类攻击） |

## 当前实测数字（2026-10-02）

以下数字来自私有引擎仪器生成的回执。它们是观测值，不是保证；仪器每周演化，引擎每次变更都会重跑。

- **MKR 16/16 = 100%** —— 16 类注入的证据篡改（数字改错、数据截断、面板过期、伪造摘要、日期偏移、覆盖缺口）全部击杀，零幸存。每个变异类都是从生产事故或红队轮次中还原的真实攻击形状。
- **CHR 15/15 = 100%** —— 5 轮校准 15 次金丝雀注入全部亮红。金丝雀层专门测试审计器能否发现*校准本身被造假*——「头条没有重算过程」被认定为结构上不可审计。
- **红队语料：52 件对抗样本，0 穿透** —— 对抗性 LLM 在 32 类攻击中生成攻击样本（含来源改写、延迟审计重放覆写、文件名逃逸、宣称与数据脱钩）。全部被拦截；每周 cron 持续演化新攻击类。
- **独立审计轮次：v0.9.40 上线前连续 6 轮 BLOCK→修复→PASS** —— 引擎变更不靠作者自测上线。非作者审计员攻击每次变更；仅 v0.9.37 就经历五轮 BLOCK（锚定注册表投毒、TOCTOU 写竞态、相对命名空间分裂）才通过。

## 数字背后的纪律

那六轮审计烧出了四条原则：

1. **豁免 ≠ 验证。** 被跳过的检查证明不了任何事。证据缺失一律 fail-closed。
2. **收集面必须闭环。** 一个能被静默跳过的检查，比没有检查更糟。
3. **未声明即欺诈。** 没有声明的capability被宣称，是审计发现，不是营销话术。
4. **Fail-closed 不能误伤。** 107 个真实目录干净通过同一套守卫——正是这套守卫杀掉全部 52 件攻击样本。

## 这些东西跑在哪

完整引擎——变异探针、金丝雀校准、红队语料、密封候选准入、HMAC 签名授权——已在真实量化生产线上运行，那里一个错误的 PASS 就意味着真金白银的损失。公开仓库提供审查层（CLI、GitHub Action、DeepSeek 插件）与有边界的认知层裁决；上述实测的审计功率栈通过 Audit Sprint 与设计合作伙伴试点开放。

## 复现回执形状

公开样例回执展示了这些闸门输出的裁决格式：

```bash
curl -sS https://falsify.site/examples/sample-block-report.json | python -m json.tool
```

## 边界

本页数字描述私有引擎的实测审计功率。它们不构成「任何公开产物都通过了这些门」的宣称；这里的任何 PASS 都不授权部署、交易或资金动作。只做审查签收。
